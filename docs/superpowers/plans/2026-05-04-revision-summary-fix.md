# Revision Review Summary Fix Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Surface the reviewer's `review.body` (the summary text typed into the GitHub review form) into the revision prompt so the agent acts on summary-only reviews instead of no-op'ing, and hard-fail when a revision run has zero feedback content.

**Architecture:** `router/src/helpers/build-revision-context.ts` already loads the latest CHANGES_REQUESTED review and emits `review_comments_json` for inline thread comments only. We add a sibling `review_summary` variable populated from the review's `body`, render it into all three revision fragments, and throw when both `review_summary` and `review_comments_json` are empty (mirrors the existing "no REQUEST_CHANGES review" throw at line 74).

**Tech Stack:** TypeScript, Vitest, esbuild, Markdown prompt templates with `{{var}}` interpolation.

**Triggering bug:** konfirmity/frontend#2876 iteration at 2026-05-04 12:01–12:07. samkit-jain submitted a CHANGES_REQUESTED review with body `"pnpm run build is failing"` and no inline comments. The agent received `review_comments_json: "[]"`, posted "Revision run found no review comments to address", and pushed nothing. State machine still advanced to `impl-in-review`.

**Out of scope:** HEAD-moved-or-fail verification in the impl job (separate defensive insurance, tracked elsewhere).

3. If the reviewer leaves a completely empty review (no summary, no inline) the workflow should now fail loudly with the `no actionable feedback` error rather than silently advancing state. That failure should be considered correct behaviour, not a regression — the reviewer needs to actually say what they want changed.
